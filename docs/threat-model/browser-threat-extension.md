# Browser Threat-Model Extension

**Version:** 0.3 (2026-07-07: C-1 closed for non-host peers by wallet transport v0.3 host attestation, ADR-013) · Extends the wallet threat model (`wallet/docs/threat-model/threat-model.md`, threats T-01…T-26) with browser-specific threats. Same asset/attacker taxonomy; IDs continue as BT-xx.

**Review status:** Reviewed 2026-07-07 against the then-current wallet threat model (T-01…T-26) for browser MVP gate criterion 5. Each row now carries a **disposition**: *mitigate-MVP* (must be built/validated for the product MVP), *accept-label* (accepted for the MVP with an honest user-facing label, per the wallet's `accepted-P` discipline), or *defer-trigger* (out of MVP scope; named trigger reopens it). This review supersedes the v0.1 "design-stage, no code exists" framing: the transport (T-18), the Vault process split (T-03/T-04), and the trusted confirmation surface (T-12) are now implemented in the wallet, which changes several mitigations from intent to fact.

## Standing conclusion for the engine decision (resolved)

v0.1 flagged BT-01 (capsule escape, favors Chromium-class isolation) vs BT-11 (update burden, favors WebView shells) as the open engine question. **ADR-B002 resolved it with harness data:** the isolation that matters is split between the wallet (permission scoping — already enforced, engine-independent) and the host process (capsule_id integrity — C-1). Since per-site process isolation is *not* required to get correct permission scoping, the WebView shell's lighter BT-11 posture wins; BT-01 is handled by WebView-per-capsule storage plus host-vouched capsule identity rather than by a Chromium fork.

## Review record 2026-07-07 — open items dispositioned

- **C-1 (capsule_id integrity) — CLOSED for non-host peers (wallet ADR-013), residual accepted.** v0.1→ measured that a same-user process could forge another capsule's `capsule_id` and inherit its grant (ADR-B002 finding 1; BT-01/BT-03/T-19). **Now:** transport v0.3 adds **host attestation** — a connection must present the wallet's launch token before it may assert any capsule identity, so a peer that is not the launched host is refused (`attestation_required`) and cannot forge a capsule id. Proven over the real socket (wallet `unattested_peer_cannot_forge_capsule_identity`; capsule-isolation measurement 2 now asserts closure). **Residual (accepted):** a same-user attacker who can read the launch token can impersonate the host — that is local malware (wallet T-14, `accepted-P`); per-capsule OS isolation from the engine is the defence-in-depth complement. **MVP disposition:** the transport-level prerequisite is met; the Tauri host, when built, becomes the attesting party against this same contract.
- **C-2 (residual, labeled) — confirmation-surface spoofing tiers.** BT-05 tier v1 (system dialog + secret phrase) does not defeat an attacker who already has same-user read of the phrase file, and has no occlusion detection. **Disposition:** accept-label for the MVP (wallet claims-register SC-11 keeps "trusted surface" qualified); SEP/biometric binding + occlusion detection tracked as the next tier (wallet ADR-012).
- **No new criticals** were surfaced by this review against T-01…T-26. Every BT row maps to an existing wallet threat and inherits its prototype status; the browser-specific residuals are C-1 and C-2.
